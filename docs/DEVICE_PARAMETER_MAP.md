# Device parameter map

Every mixer setting of the card is one byte in one of two **pages**. The
vendor library registers all of them when it loads, and this document is
that list, extracted and cross-checked against the captures.

Addressing, as it goes on the wire:

```
address = page * 256 + offset                     (offset = the byte in the page)
digits  = base-128, two big-endian digits         (SysEx data bytes are 7-bit)
frame   = F0 43 10 | 3E 14 01 | 01 00 <flag> | <id> 00 00 | ... | <value> F7
          <flag> = high digit, <id> = low digit
```

So `flag` and `id` are not two fields: they are the two halves of one
address, and `page 1` starts at `0x100` because a single 7-bit byte
cannot hold it. That is the same constraint that makes *values* travel as
three base-128 digits (`docs/MIC_CONTROL_PROTOCOL.md`).

## Evidence

The map is not a guess: every address the vendor application was captured
writing resolves to the parameter the driver implements.  The shape of
the four-band MIC EQ block is the clearest check - the captures showed
`0x24` shaping, `0x28`-`0x2b` gains, `0x2c`-`0x2f` frequencies and
`0x30`-`0x33` Q (all with `flag 0x02`), and the map has exactly

```
0x120-0x123  mic_eq_v2_1..4_ONF
0x124-0x127  mic_eq_v2_1..4_SHAPE
0x128-0x12b  mic_eq_v2_1..4_G
0x12c-0x12f  mic_eq_v2_1..4_F
0x130-0x133  mic_eq_v2_1..4_Q
0x134-0x137  game_eq_v2_1..4_ONF   (the GAME EQ, same layout)
```

The mic chain (`page 0`) matches the driver's ids one for one
(`0x02 MicGateOnf`, `0x03 MicGateLevel`, `0x09 MicCompOnf`,
`0x11 MicEqOnf`, `0x21 MicLimiterOnf`, ...), and the read requests the
application sends when a screen opens (`flag 0x02`, ids `0x08`-`0x0b`) are
the four `dirty_*` flags of `page 1`: that is why they answer with a
status and not with a parameter value.

`tests/test-device-map.sh` asserts all of this against the committed map,
so the document cannot drift from the file it describes.

## How to regenerate

```sh
tools/vendor/extract-device-map.py VENDOR/MemAPI_ZG01.dll \
    tools/vendor/device-map-zg01.json
tools/vendor/render-device-map.py tools/vendor/device-map-zg01.json \
    docs/DEVICE_PARAMETER_MAP.md
```

The extractor reads the library's initialiser: one record per parameter,
built as `mov dword ptr [record+0x20], 0x0001 SS II` followed by the name
and record pointers.  `kind`, `page` and `offset` come from the immediate,
the name from the string the registration call passes.  The same script
works on `MemAPI_ZG02.dll` (the newer card, which adds pages).

## Blocks

| Page | Offsets | Function |
|---|---|---|
| 0 | `0x00`-`0x01` | microphone P48V and mute |
| 0 | `0x02`-`0x08` | GATE: on, level, threshold, range, attack, hold, decay |
| 0 | `0x09`-`0x10` | COMP: on, level, threshold, ratio, attack, release, knee, out gain |
| 0 | `0x11`-`0x12` | microphone EQ on, effect name |
| 0 | `0x13`-`0x20` | microphone EQ, three bands (high/mid/low: on, shape, gain, freq, Q) |
| 0 | `0x21`-`0x27` | LIMITER: on, level, threshold, attack, release, knee, out gain |
| 0 | `0x28`-`0x2b` | microphone output level and the `mic_func*` slots |
| 0 | `0x2c`-`0x4b` | VOICE: pre-voice, transformer (formant, pitch), FX (radio), reverb |
| 0 | `0x4c`-`0x5a` | VOICE tone control, three bands (same layout as the mic EQ) |
| 0 | `0x5b`-`0x5f` | sound effect (on, level, dB level, frequency, waveform) |
| 0 | `0x60`-`0x6f`+ | echo (on, stereo, time, level, ...) |
| 1 | `0x00`-`0x18` | monitor EQ, HDMI select/mute/version, LED, dirty flags, streaming levels/mutes |
| 1 | `0x1b`-`0x1f` | voice effect levels (harmony, pitch, radio, tremolo) |
| 1 | `0x20`-`0x33` | MIC EQ v2, four bands |
| 1 | `0x34`-`0x47` | GAME EQ v2, four bands |
| 1 | `0x48`+ | monitoring, USB/out routing, other status |

Note that the three-band microphone EQ (`0x13`-`0x20`, `mic_eq_hi/md/lo`)
and the four-band one (`0x120`-`0x133`, `mic_eq_v2_*`) are different
blocks: the ZG Controller's MIC EQ editor drives the second one.

## Limits

- The map gives **addresses and names**, not value semantics: ranges,
  units and enumerations come from the vendor parameter model
  (`docs/PARAMETER_INVENTORY.md`) and from the captures.
- Records of `kind 2` (the `meter_*` inputs) share records with controls
  and are **not** part of this map: meters are read-only and are not
  addressed the way parameters are.
- Only `MemAPI_ZG01.dll` is extracted here; the ZG02 has more pages.
